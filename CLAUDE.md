# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Paul Dirac (1902–1984) formulated the Dirac equation, predicted antimatter, and laid the foundations
> of Fermi-Dirac statistics. The Dirac project implements **MicroProfile Metrics 5.1.1**:
> it measures application state with precision — counters, gauges, histograms, timers —
> and exposes them in a standard format (OpenMetrics / Prometheus), without ever altering
> the observable through observation.

## Prerequisites

- **Java 25** + **Maven 4.0.0-rc-5** (`.sdkmanrc` provided — use `sdk env`)
- The out-of-reactor TCK runner consumes Dirac artifacts installed locally by the
  `run-official-tck-mp-metrics-5.1.sh` script

## Architecture

Dirac is a **MicroProfile Metrics 5.1.1** implementation with zero implementation
dependencies: only the specified Jakarta EE and MicroProfile APIs are used.

```
dirac-api            ← MP Metrics 5.1.1 spec wrapper + Vidocq SPI (MetricRegistryProducer,
                       DiracContext); stable public types: MetricID, Tag, Snapshot
dirac-core           ← Pure Java 25 implementations without CDI (CounterImpl, GaugeImpl,
                       HistogramImpl, TimerImpl, MetricRegistryImpl, OpenMetricsFormatter,
                       JsonMetricsFormatter)
dirac-cdi-vauban     ← CDI interceptors + BCE Vauban (DiracExtension) for @Counted,
                       @Timed, @Gauge; @ApplicationScoped producers for MetricRegistry
dirac-rest           ← JAX-RS GET /metrics endpoint (OpenMetrics / Prometheus text format)
                       via Cassini; optional — activated if cassini is on the classpath
dirac-bench          ← JMH benchmarks vs Micrometer / SmallRye Metrics
dirac-tck            ← Official TestNG+Arquillian TCK runner (out-of-reactor — Model 4.0.0)
dirac-examples       ← Standalone and vidocq-mps usage examples
```

**Current actual state:** M1, M2, M3 (core), M4, M5, M6, and M7 are complete; M8 (official TCK) is the next step. Production classes already present include
`io.vidocq.dirac.api.DiracException`, `io.vidocq.dirac.internal.CounterImpl`,
`io.vidocq.dirac.internal.MetricRegistryImpl`, `io.vidocq.dirac.internal.GaugeImpl`,
`io.vidocq.dirac.internal.HistogramImpl`, `io.vidocq.dirac.internal.TimerImpl`,
`io.vidocq.dirac.internal.BaseMetricsRegistrar`,
`io.vidocq.dirac.internal.OpenMetricsFormatter`,
`io.vidocq.dirac.internal.JsonMetricsFormatter`,
`io.vidocq.dirac.api.TimerSnapshot`,
`io.vidocq.dirac.cdi.internal.DiracExtension` (validation/resolution of `@Gauge`),
`io.vidocq.dirac.cdi.internal.MetricRegistryProducerBean`,
`io.vidocq.dirac.cdi.internal.CountedInterceptor`,
`io.vidocq.dirac.cdi.internal.GaugeRegistrationBean`, and
`io.vidocq.dirac.cdi.internal.TimedInterceptor`,
`io.vidocq.dirac.rest.MetricsEndpoint` (placeholder), as well as the benchmark
`io.vidocq.dirac.bench.M4TimerBenchmarks`. Most items described above remain the M8 target (full TCK).

Concrete API note: the `microprofile-metrics-api:5.1.1` JAR used here does not expose
the annotation `org.eclipse.microprofile.metrics.annotation.Histogram`; the CDI part of M3
depending on this annotation is therefore blocked until this point is resolved.

A CDI integration test `@Counted` with embedded Vauban is present in
`dirac-cdi-vauban/src/test/java/io/vidocq/dirac/cdi/internal/CountedInterceptorCdiIntegrationTest.java`.

The packages actually present on the production side are `io.vidocq.dirac.api`,
`io.vidocq.dirac.internal`, `io.vidocq.dirac.cdi.internal`, and `io.vidocq.dirac.rest`.

**Fundamental separation:** `dirac-core` contains the data structures and metric registrations
(pure logic, thread-safe via `LongAdder`, `AtomicReference`, nanoTime). `dirac-cdi-vauban`
carries the CDI interceptors that delegate to the core. This allows the registry and metrics
to be unit-tested without a CDI container.

**Metric registry:** `MetricRegistryImpl` maintains a
`ConcurrentHashMap<MetricID, Metric>` per scope (`APPLICATION`, `BASE`, `VENDOR`).
`MetricID` is an immutable value `(name, Set<Tag>)`. The APPLICATION registry is
injectable via CDI; BASE and VENDOR are populated at startup by `DiracExtension`.

**Intercepted measurement flow (e.g. `@Counted`):**
CDI intercepts the call via `CountedInterceptor.around()` →
resolves the `MetricID` (cache by `(BeanClass, Method)`) →
increments the `Counter` in the APPLICATION `MetricRegistryImpl` →
delegates to `ctx.proceed()`.

**Export format:** OpenMetrics / Prometheus text format (`text/plain;version=0.0.4`) via
`OpenMetricsFormatter` in `dirac-core`. Optional REST endpoint in `dirac-rest`.

## Architecture Constraints Not to Violate

1. **Zero implementation library imports in `dirac-core`** — only spec APIs:
   `microprofile-metrics-api`. No Micrometer, Dropwizard Metrics, SmallRye Metrics.
2. **No `synchronized`, no `ThreadLocal`** — mandatory virtual-thread-friendly.
   Use `LongAdder`, `AtomicLong`, `AtomicReference`, `ConcurrentHashMap`.
3. **No `setAccessible(true)` in production** — use `MethodHandles.privateLookupIn`
   if internal access is needed; document any `opens` in `module-info`.
4. **No `java.lang.reflect.Proxy`** for `@Gauge` resolution — resolution via
   `MethodHandle` at container startup (BCE `DiracExtension`).
5. **`dirac-tck/pom.xml` stays at Model 4.0.0** — do not move to 4.1.0 until
   ShrinkWrap is updated (constraint common to the entire Vidocq ecosystem).
6. **TCK 100% PASS is a hard contract** — any structural modification to `dirac-core`
   or `dirac-cdi-vauban` must preserve this score before merge.
7. **Thread-safety without contention** — metrics are hot paths; prefer
   `LongAdder` over `AtomicLong` for counters under high concurrency.

## Conventions

- **Explicit Java modules**: `dirac-api` already has its `module-info.java` under `src/main/java/`;
  `dirac-core` and `dirac-cdi-vauban` keep theirs under `src/main/module-info/`;
  `dirac-rest`, `dirac-bench`, and `dirac-examples` don't yet have a `module-info.java` in the
  current state and neutralize the inherited parent `compilerArgs` in their `pom.xml`.
- **Packages**:
  - `io.vidocq.dirac.api.*` — stable public SPI (MetricRegistryProducer, DiracContext, Snapshot)
  - `io.vidocq.dirac.internal.*` — internal code, not exported (implementations, formatter)
  - `io.vidocq.dirac.cdi.*` — CDI integration (interceptors, BCE, producers)
  - `io.vidocq.dirac.rest.*` — JAX-RS endpoint (optional)
- **Maven groupId**: `io.vidocq.dirac`
- **Records**: prefer immutable records for `MetricID`, `Tag`, `HistogramSnapshot`,
  `TimerSnapshot`, `GaugeConfig`, `TimerConfig`, `HistogramConfig`
- **Sealed interfaces**: `Metric` remains the root interface; `Counter`, `Gauge<T>`,
  `Histogram`, `Timer` are the sealed subtypes of the internal implementation
- **Pattern matching**: use `switch` on sealed types in `OpenMetricsFormatter`
- **LongAdder / DoubleAdder** for high-frequency counters and accumulators
- **`System.nanoTime()`** for timers — never `System.currentTimeMillis()`
- **Virtual threads** for concurrency tests and JMH benchmarks
- **Language** — commit messages, Javadoc, and all `.md` file content must be written in **English**.

## TDD Methodology

- **Red → Green → Refactor** — no production line without prior test.
- Cite the MicroProfile Metrics 5.1.1 spec section in test Javadoc/comments.
- Unit tests in the same package as the tested class, named `<Class>Test`.
- No Mockito — manual doubles (`FakeMetricRegistry`, `FakeInvocationContext`, etc.).
- CDI integration tests via embedded Vauban (without Arquillian) in `dirac-cdi-vauban`.
- JMH benchmarks in `dirac-bench` — comparison vs Micrometer and SmallRye Metrics from M4.
- Prioritize completing existing placeholders (`DiracExtension`, `MetricsEndpoint`)
  before introducing parallel functional entry points.

## Plan Mode Default

- Enter plan mode for any non-trivial task (adding a metric type,
  refactoring `MetricRegistryImpl`, modifying the OpenMetrics format).
- Document architecture decisions in `ROADMAP.md` (section "Documented decisions").
- Use the `virtual-threads-reviewer` agent for any concurrent code modification.
- Use the `jpms-guardian` agent after any package addition or `module-info.java` modification.

## Available Agents

- `classfile-codegen` — if `@Gauge` resolution requires bytecode generation
- `virtual-threads-reviewer` — for `TimerImpl` (nanoTime + LongAdder), concurrent access
  to `MetricRegistryImpl`, any concurrent or performance-critical code
- `jpms-guardian` — after `module-info.java` modification or package addition
- `dependency-gatekeeper` — before any `pom.xml` dependency addition
- `tck-runner` — to diagnose MicroProfile Metrics 5.1.1 TCK failures
